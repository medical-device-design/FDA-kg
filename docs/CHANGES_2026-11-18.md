# Changes, November 18, 2026: FAERS report copies get their own nodes

## The problem

FRINK's first build of fda-drug-event-kg (stable_v0_0_1, November 16) had 20,690,879
AdverseEventReport nodes for 20,692,690 FAERS records. openFDA lists 1,811 safetyreportid values
twice. The L1 build gave both copies the same IRI, so their values merged on one node. FRINK's
VoID showed the symptoms:

| Symptom | Count |
|---|---|
| Report nodes with two transmission dates | 1,811 |
| Report nodes with two receive dates | 15 |
| Drug nodes with two medicinalproduct values | 2,068 |
| Reaction nodes with two reaction terms | 504 |

## What the duplicates are

`scripts/faers_split/faers_dup_versions.py` read the 1,767 bulk partitions for the 1,811 ids
(`dup_versions.tsv` on the VM). All 1,811 are old AERS reports from 2004 to 2010 with no
safetyreportversion. The two copies differ in transmissiondate. 565 pairs sit in the same
partition and 1,246 in two partitions. The live openFDA API returns both copies too (checked for
5091278-2, 6287641-4, 6165059-2 and 4642347-X, each `total 2`), so they are two records in the
source, not an export artifact.

## The fix (option A, Roche, November 18)

Every copy keeps its own node. The first copy in sorted partition order keeps `report/<id>`, and the
second gets `report/<id>-2`, in every IRI of its group (report, patient, drugs, reactions,
openfda blocks). This is the same rule as the repeated Import Alert listings (November 8). Nothing
is dropped. Report ids in the source use a hyphen that the IRI slug turns into an underscore, so
`-2` cannot collide with a real id.

The corrected files were made by a stream pass over the published files
(`faers_split_versions.awk`), not a rebuild, so every triple outside the 3,622 affected report
groups is byte-identical. The pass reads each report group (children first, report node last).
A group whose report node has been seen once already is relabeled.

| File | Report groups | Duplicated groups | Relabeled |
|---|---|---|---|
| drug_event.ttl.gz | 19,818,058 | 3,550 | 1,775 |
| drug_event_part2.ttl.gz | 874,632 | 72 | 36 |
| l2_term_text_faers.ttl.gz | 20,692,686 | 3,621 | 1,810, plus 1 by `fix_adj.sh` |
| l2_meddra_faers.ttl.gz (VM only) | 20,692,685 | 3,621 | 1,810, plus 1 by `fix_adj.sh` |

The L2 files have no report node to close a group, so the one pair whose copies are adjacent in
one partition (7010949-1) fell into one group there. `fix_adj.sh` relabeled its second run of
reactions (11 lines in each file).

## Pipeline

So the next full build gives the same IRIs:

- `pipeline/l1_openfda_any.py`: drug/event has `split_repeats=True`. The n-th copy of a report id
  in sorted partition order is `report/<id>-n`.
- `pipeline/l2_term_text.py` and `pipeline/l2_meddra_terms.py`: the FAERS workers return per-report
  records and the parent numbers the copies in the same order.

## Publication

The three corrected files replaced `drug_event.ttl.gz`, `drug_event_part2.ttl.gz` and
`l2_term_text_faers.ttl.gz` on fda-drug-event-kg develop and were merged to main (Roche's yes,
November 18, 18:01). Log: `logs/lakefs_faers_split_2026-11-18.log` on the VM. The local copies of
the old files were deleted first to keep 100 GB free on the shared volume (the old versions stay
in lakeFS history). A new FRINK build follows. The November 16 stable_v0_0_1 build was not tagged.

## For users

20,692,690 report nodes, one per openFDA record. To count cases rather than records, group by
`ex:safetyreportid` (1,811 ids have two nodes, told apart by `ex:transmissiondate`).
