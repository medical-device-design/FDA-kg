# Changes, November 8, 2026: full-FAERS link check, same-file duplicate-subject audit, import-alert fix

Follow-up to the VAERS child-IRI collision of November 7. Two questions: do the other L1 files have
the same kind of collision, and how many FAERS links point at nodes that do not exist (the October 28
link report skipped FAERS; the November 7 sample found two). Script: one pass on the VM,
`logs/faers_links_2026-11-08.log`, scratch `work/faers_links/`.

## 1. Same-file duplicate subjects (58 L1 files, six graphs plus VAERS v2)

Test: a subject IRI written as a block more than once in the same file. 47 files have none. The 11
with repeats:

| Verdict | File (duplicate subjects) | What it is |
|---|---|---|
| Identical blocks, harmless | orangebook_files (54), historical_document (4), tobacco_digital_ads (2), tobacco_marketing_orders (2, differ only in `ex:sourceRecordId`) | the source repeats the row; every store deduplicates |
| Same entity from several rows, values merged on the right node | unii.ttl (3,071 UNIIs with two names, e.g. "DL-SERINE" and "SERINE, DL-"), ndc_companion (2,264 package NDCs listed under two SPL versions with their own marketing dates), ndc (4), drug_label (5 set ids), shortages (1), vaers_v2 (68,389 VAERS_IDs with more than one DATA row, the known case) | the IRI is the entity's natural key, so one node with all values is right; nothing to change |
| **Collision, same kind as VAERS** | **import_alerts.ttl** (1,274: 247 firm entries and 1,027 products) | a firm listed twice in the same alert list (same name and address, its own date and products each time) got the same hash key, so the second entry's products landed on the first entry's `product/1` |

Fix in `pipeline/l1_import_alerts.py`: a repeated firm key gets `-2`, `-3` ... so every unaffected
IRI stays as published. Rebuilt as `out/fda-compliance-kg/import_alerts_v2.ttl`: 0 duplicate
subjects, 265 suffixed entries carrying 1,261 products, the same 153,004 typed nodes, 1,368,613
triples, riot clean, SHACL conforms. Replacing the published `import_alerts.ttl` waits for the PI's word.

Not covered by this test: a collision between two different source rows that share a natural key
in the source itself (a package NDC under two SPL versions is the example above). Those are
source facts and are kept as merged values.

## 2. FAERS links, full file (20,692,690 reports, both files)

| Link | Distinct targets | Resolve to a declared node |
|---|---|---|
| `ex:hasApplication` -> fda-drug-biologic-kg application | 11,711 | 11,711 (100 %) |
| `ex:hasPackageNdc` -> fda-drug-biologic-kg ndc-package | 130,648 | 130,646 (two missing) |
| `ex:hasSubstance` -> fda-substance-kg unii | 3,819 | 3,819 (100 %) |

The two missing package NDCs are `0023-0796-15` and `0023-0797-05` (an Allergan labeler code),
present in no current NDC Directory, companion or NSDE file, so they are delisted packages that
openFDA's harmonized block still carries. Stubs written with `l2_stubs_all.py` as
`fda-drug-biologic-kg/l2_stubs_faers.ttl` (2 NdcPackage stubs, 10 triples, riot clean, conforms).
These are the same two the November 7 sample found, so the sample was representative.

Also seen: 1,811 FAERS report IRIs appear twice (the same `safetyreportid` in two export
partitions, 0.009 % of reports). The report IRI is the natural key, so one node; where the two
copies differ their values are merged. Noted, not changed.

Declared nodes counted for the check: 711,877 ndc-package, 31,760 application, 173,165 unii.
