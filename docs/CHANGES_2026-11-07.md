## VAERS: two defects found by the full query run, both fixed in the pipeline

1. `NonDomesticVAERS*.csv` sits inside both snapshot zips and the L1 build read it twice.
   Identical blocks, so stores deduplicate them, but the file total was inflated (200.9 M
   triples, 3,622,202 "reports"). `l1_vaers.py` and `l2_term_text.py` now read a member name once.
2. Vaccination and symptom child IRIs were keyed by the CSV's `ORDER` column
   (`vaers-report/<id>/vax/<ORDER>`). `ORDER` is "1" on 97 % of rows and repeats within a report,
   so rows of the same report collided: 3,444,928 vaccination rows became 2,811,621 nodes and
   3,774,947 symptom rows became 2,811,342 nodes. Every value is still present on the merged node,
   but the row grouping (which vaccine type goes with which lot, manufacturer and dose) is lost for
   633,307 vaccination rows (18 %) and 963,605 symptom rows (26 %). The child IRI is now the row's
   1-based sequence within its report in file order; `ORDER` is kept as `ex:order`.
   `l2_term_text.py` uses the same sequence so the symptom text lands on the right node.

Rebuilt on the VM as `vaers_v2.ttl.gz` (157,526,636 triples; 2,811,621 report blocks, 3,444,928
vaccinations, 3,774,947 symptom sets, one node per row) and `l2_term_text_vaers_v2.ttl.gz`
(11,961,420 triples). riot clean, SHACL conforms on a 3 M-line sample. The published files on
lakeFS (`vaers.ttl.gz`, `l2_term_text_vaers.ttl.gz`, merged to `main` the same evening) still carry
the old IRIs: replacing them on `develop` and re-merging before the first tag is recommended and
waits for the PI's word. The VM-only `l2_meddra_vaers.ttl.gz` code links are keyed by the old
symptom-set IRIs and need the same rebuild if they are ever used.

A report whose rows appear in two files (23,628 ids in both a yearly and the NonDomestic file) now
gets one child node per row, so its vaccinations may be listed twice with identical values; that
is faithful to the source rows and is noted here rather than deduplicated.
